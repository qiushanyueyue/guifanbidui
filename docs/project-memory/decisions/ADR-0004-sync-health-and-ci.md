# ADR-0004：同步批次质量门与服务/数据健康分离

- status: `accepted`
- date: `2026-10-03`
- owners: 项目维护者与代码代理

## 背景

`verify_v2_csres.py` 将部分失败视为可继续发布的批次，包括全部候选失败。已有 V2 发布质量门关注数据关系，不能替代来源抓取健康检查。普通搜索与编号查找对 GB/GB-T 身份演进的处理也不一致。

## 决定

- 普通搜索和编号查找共用数据库身份匹配：显式版次优先，其次最佳记录；只允许同序号、同年份的 GB↔GB/T，不扩展为任意行业前缀别名。别名命中仍由 matcher 输出属性修正。
- 日/周/月任务先尝试发布已取得的证据，再检查本次同步 ID；使用本地 run-id 文件传递批次，不查询“最新批次”代替当前批次。
- 完成且状态为 success/partial、计数合法、至少一项成功、失败率不超过 50% 才通过；明确 success 的 0/0 空跑允许通过。failed/running/未完成、全失败和非法计数都失败。
- 发布步骤失败时仍执行来源质量检查，保留两种失败；不关闭现有数据关系质量门。同步工作流共用串行 concurrency group，避免定时任务互相覆盖。
- `/api/health` 保留原字段，新加 `data` 和 `reasons`。服务可正常提供历史库时顶层仍为 ok，数据异常单独为 degraded。
- 数据异常条件：空库、unknown 占比超过 5%、存在 conflict、无取得可用记录的已完成批次、此类批次距今超过 3 天、最近已完成批次失败率超过 50% 或状态失败。5% 是明确判断率 95% 的覆盖目标；reasons 区分覆盖与管线故障。
- `last_successful_sync` 指至少取得一条可用记录的已完成 success/partial 来源批次，不表示全库已经核验，也不表示发布质量门通过。空跑不能刷新该时间。
- CI 使用隔离 SQLite/PostgreSQL，禁止连接生产库，执行测试、迁移幂等、仓库 seed 黄金案例、前端测试/lint/build 和记忆检查。目录审计测试从公开归档的 raw_value 重放，不依赖个人磁盘路径。

## 后果与边界

这批变更修复查询一致性与监控表达，不会修复来源网站访问/解析、清理生产替代关系或接通官方适配器。CI 成功、API 健康和 Vercel Ready 分别只证明各自检查结果。生产数据治理仍需要独立授权、证据和验收。
