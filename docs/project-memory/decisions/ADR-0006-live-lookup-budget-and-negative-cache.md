# ADR-0006：查询时联网复核总时限与负缓存

- status: `accepted`
- date: `2026-10-24`
- owners: 项目维护者与代码代理
- refines: [`ADR-0003`](ADR-0003-decisive-freshness-aware-verification.md) 中“有界联网复核”的“有界”定义

## 背景

ADR-0003 要求 `/api/v1/verify` 对过期、异常或漏收记录做有界联网复核，但原实现只限制了单次 HTTP 超时（10 秒）并保留默认 3 次重试和最长 30 秒的 `Retry-After` 等待。发现流程对多个来源、编号与名称各查一次，最坏耗时可达数分钟，超过 serverless 函数时限，用户只看到失败。另外 `unknown/conflict` 永不新鲜，生产约 66% 条目为 unknown，几乎每次查新都会重新访问第三方来源，拖慢页面并增加被限流风险。

## 决定

- 每个 `/api/v1/verify` 请求设一个共享的单调时钟截止时间，默认 8 秒，由 `LIVE_LOOKUP_BUDGET_SECONDS` 调整（最小 1 秒）。查询时创建的 HTTP 适配器关闭重试，单次超时取“默认超时”和“剩余预算”的较小值；预算耗尽后，后续来源直接以 `RequestTimeout` 失败，不再发起网络请求。定时同步脚本不设截止时间，保持原重试策略。
- 新增 `live_lookup_attempts` 表作为负缓存：键为 `code:<规范化编号>`，没有编号时为 `name:<规范化名称>`，记录最近尝试时间和结果（`found` / `miss` / `budget_exhausted`）。同一键在 `LIVE_LOOKUP_RETRY_HOURS`（默认 24 小时）内不再重复联网发现或复核。
- 负缓存只是调度信息，不是状态证据：它不修改 `last_verified_at`、来源证据或业务状态。成功复核得到明确状态后，记录仍按 30 天新鲜期判断；复核失败时保留历史结论。
- 前端所有请求统一设 20 秒超时（导出 60 秒），每次提取、重新查新或清空都会开始新的一轮查新：上一轮未完成的请求被取消，迟到的结果被丢弃。

## 替代方案

- 只缩短单次 HTTP 超时：无法限制多来源、多查询词叠加后的总耗时，不采用。
- 在 `standards_v2` 增加“最近尝试时间”列：重建发布可能覆盖该表，且需要 ALTER 迁移；独立表由 `create_all` 增量创建，重建后仍保留，因此采用独立表。
- 把失败尝试写进 `last_verified_at`：会把“尝试过”伪装成“已核验”，违反证据时间原则，不采用。
- 用线程池强制超时：后台线程仍会继续访问来源，资源不可控，不采用。

## 后果

- 查询时最坏耗时约为预算加数据库开销，前端能在超时内得到明确的“暂无法确认”或错误状态，不再无限等待。
- 24 小时内重复查询同一 unknown 或漏收编号只读数据库；来源恢复后最多延迟一个重试窗口才会再次联网。
- 预算较紧时，排在后面的来源（如搜建筑）可能来不及查询，交叉核验比例可能下降；需要观察 `budget_exhausted` 的比例。

## 复核条件

- 生产函数时限、来源响应时间或交叉核验比例明显变化时，重新评估预算和重试窗口。
- 接通官方适配器后，确认官方源在预算内的排序和超时表现。

## 补充决定（2026-10-24，同日）

- 背景：本地实测 CSRES 详情页单次 12–20 秒、搜索页约 3 秒；已存详情 URL 时，查询时复核在 8 秒预算内全部 `budget_exhausted`。
- 决定：查询时（有截止时间）每个来源先查搜索页，搜索页未得到完全匹配且仍有预算时才查详情页；定时同步（无截止时间）仍直接取详情页。搜索页没有替代关系，因此“没有关系文本”不视为与另一来源的关系不一致：查询时合并与发布重建都只比较各来源最近一条明确的关系文本，两者都存在且不同才判冲突。已有替代关系由历史详情证据继续重建，不会被搜索页记录抹掉。
- 搜建筑返回“真人验证”等验证页时抛出 `SourceUnavailable`，按来源不可用处理，不尝试绕过。
- 后果：查询时复核主要依赖搜索页的状态，替代关系的刷新仍靠定时同步的详情页。
